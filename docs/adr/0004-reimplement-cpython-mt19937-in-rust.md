# 0004. Reimplement CPython's MT19937 rather than use a Rust RNG

| Field    | Value                                  |
|----------|----------------------------------------|
| Date     | 2026-08-19                             |
| Status   | Accepted                               |
| Deciders | theta                                  |
| Branch   | `feature/rust-port`                    |
| Commit   | `7cd14fd`                              |

## Context

The port to Rust ([[0003]]) chose byte-identical output as its acceptance
criterion, with the 42-config corpus ([[0002]]) as the oracle. That corpus was
generated by `background.py` running on CPython, and **every hexagon, triangle,
star, blind phase and rain glyph in it is a draw from CPython's `random`.**

The layout depends only on `seed`. Reproducing it therefore means reproducing
CPython's generator exactly — not merely producing "good random numbers".

This was decision #1 of four taken before the port's design began, because it
determines whether the corpus is proof or theatre.

## Decision

We will reimplement CPython's `random` module in `src/rng.rs` for the calls
this program makes:

- **MT19937 with `init_by_array`**, seeded the way `random.seed(str)` seeds:
  `n = int.from_bytes(s + sha512(s), "big")`, split into little-endian 32-bit
  words, `keyused = ceil(bits/32)`.
- `random()` = `genrand_res53`, plus `getrandbits(k)`, `_randbelow` (rejection
  sampling on `bit_length`), `shuffle` (Fisher–Yates downward), `sample`'s pool
  algorithm, `uniform`, and `choice`.

Each of these consumes a **specific number of 32-bit words**. That word count is
part of the contract, not an implementation detail.

Pinned by unit tests against vectors captured from Python 3.14.7:
`Random("trihex:0").random()` → `0.323979587515701, 0.480793333456907,
0.521798912248572`; `getrandbits(32)` → `1391481750, 664579869, 2064991622,
3668470967`; `sample(range(6), 6)` → `[2, 1, 3, 5, 4, 0]`.

`sha2` becomes a dependency: string seeding needs SHA-512 once per cell RNG, and
a hand-rolled hash is the wrong place to save eighty lines.

## Alternatives Considered

### Use a Rust RNG (`rand`, `StdRng`, anything) and regenerate the corpus

By far the cheaper path: delete a module, take a maintained dependency.

Rejected because it destroys the port's only proof. A regenerated corpus passes
because it was made to match the new code, so it cannot distinguish "the port is
correct" from "the port is different and I re-blessed it". Keeping CPython's
generator is what makes 42 byte-identical renders mean something. The cost is one
module; the payoff is the entire acceptance criterion.

### A "compatible" shortcut — same algorithm, simpler draw routines

Tempting: MT19937 is standard, so implement the core and approximate
`_randbelow` / `shuffle` / `sample` with equivalent-quality equivalents.

Rejected as the most dangerous option on the list. Each of those routines
consumes a *specific* number of 32-bit words. An implementation that produces
statistically equivalent results while consuming a different number of words
desynchronises the generator, and every draw after it is wrong. The failure is
silent and total, and it would appear as an unexplained golden mismatch far from
its cause.

### Capture the Python draw sequence and replay it

Record every value the Python version drew and ship it as data.

Rejected: it fixes the corpus's seeds forever, and the program would stop being
able to render any seed it had not pre-recorded.

## Consequences

### Positive

- The corpus became a genuine equivalence proof, which is what let both [[0003]]
  and [[0009]] claim "the picture did not move" as fact rather than intent.
- Determinism is reproducible across languages: the same seed gives the same
  layout in the Python original and the Rust port.

### Negative / Trade-offs

- A hand-written RNG module is maintained in this repo forever.
- `sha2` is a dependency solely for string seeding.
- The RNG is pinned to CPython's behaviour, so if CPython ever changed its
  `random` internals, this crate would reproduce the *old* behaviour. That is
  the correct outcome here — the corpus is the contract, not CPython — but it
  means the module is frozen rather than tracking upstream.

### Neutral

- The call *order* matters as much as the algorithm: `motion == LIGHTS` draws two
  values from the global stream inside the render loop, after triangle
  assignment. The sequence is part of the contract.

through two subsequent refactors.

### Gotchas

- **Do not swap in a Rust RNG.** `CLAUDE.md` states this as a standing rule and
  this ADR is why. It is the single change most likely to be attempted by someone
  who sees a hand-rolled RNG and assumes it is technical debt.
- **Do not "optimise" a draw routine.** Word consumption is the contract. A faster
  `_randbelow` that consumes a different number of words desynchronises everything
  drawn after it.
- Draw *order* is as load-bearing as the algorithm. Restructuring a render loop —
  for example filtering before mapping — can move a draw without changing any
  visible logic. `pat_trihex`'s eager single pass and `pat_matrix`'s
  draw-then-`continue` both depend on this.
- `cell_rng` exists so per-cell effects draw off their own stream. Keying it
  differently would reshuffle every cell.
